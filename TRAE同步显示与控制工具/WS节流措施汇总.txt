TRAE 同步显示与控制工具 —— WS 流量节流措施汇总
（本文件汇总「所有已生效的节流措施」，含原有措施与本轮新增措施）
版本：服务端 v1.51 / 手机版 v1.32        日期：2026-09-14
================================================================================

【一句话结论】
烧流量的不是 AI 推理（推理在 TRAE 进程内部，不经过本工具），而是本工具的
「实时镜像显示」机制：每 0.8 秒拉一次全量快照，只要里面变一个字节就整包
重发——含该会话的全部历史消息。本轮的核心措施是：**建立客户端登录概念，
没人登录就一条都不发**。


────────────────────────────────────────────────────────────────────────────
一、流量为什么大（根因，详见《WS流量整改交接文档_给AI看.txt》）
────────────────────────────────────────────────────────────────────────────
1. 轮询：poll_sec 默认 0.8 秒拉一次快照（100% 复刻 TRAE 界面）。
2. 快照含整个会话的全部消息 msgs，**没有条数上限**，会话越长越胖。
3. 去重是「整包 MD5 指纹」：AI 流式生成时几乎每 0.8 秒指纹就变 →
   整个会话（含全部历史）每次整包重发。
4. PieSocket 单消息 16KB 上限，>10KB 自动切段，**每段按 1 条计数**，
   条数虚高。
5. 多端广播扇出：服务端发 1 次，手机端 + 本地面板 + 多服务端各收 1 次。
放大结果：多端合计每天近 10 万条。


────────────────────────────────────────────────────────────────────────────
二、原有节流措施（1.00 ~ 1.50 已有，本次保留）
────────────────────────────────────────────────────────────────────────────

A1. 快照内容指纹去重（服务端 forward_event）
    · 对整包快照算 MD5 指纹，与上一拍相同 → 不重发。
    · 作用：TRAE 界面静止时零发送（最基础的一道闸）。
    · 局限：AI 打字时内容一直在变，指纹每拍都不同 → 挡不住。

A2. 掉线期只缓存不排队 + 重连整包重放
    · WS 断开期间不把快照堆进发送队列（否则重连后一次性倾泻）；
      只保留「最新一包」；重连后 hello 重放最新快照 + 模型列表。
    · 作用：断网/切网期间零流量，恢复后只补一包。

A3. FOX 分段协议（16KB 上限）
    · PieSocket 单消息 16KB，>10KB 自动切段发送。
    · 作用：避免超限被中继整条丢弃（可用性措施，不是省量措施；
      实际上分段会让计数偏高）。

A4. WS 链路心跳 25 秒（'ping'，4 字节）
    · 仅用于保活防中继空闲断连，量极小，可忽略。

A5. 多服务端身份心跳 20 秒 / 75 秒超时
    · 多台服务端同频道时的互相发现（srv 报文，带版本/端口/在线集）。
    · 量小；未命名时不广播。

A6. 客户端渲染指纹跳重画（手机版 renderMsgs / renderConvs）
    · 收到快照后按整包 key 比对，相同则不重画 DOM。
    · 作用：省手机 CPU/电量，不省流量（包已经收到了）。

A7. 占位卡与排队条交接（v1.50 / v1.31d）
    · 发送中占位卡与插话队列面板不重复显示两张卡。
    · 省的是渲染与观感，非流量。


────────────────────────────────────────────────────────────────────────────
三、本轮新增措施（★ 核心：客户端登录态闸门）
────────────────────────────────────────────────────────────────────────────

B1. 建立「客户端登录」概念（服务端 v1.51）
    · 客户端上线/回到前台时发 {'t':'login','fg':bool}，服务端据此登记
      「有人在线」；在线期间每 60 秒发一次 {'t':'hb'} 心跳。
    · 心跳超时判下线：LOGIN_TMO = 150 秒无心跳 → 判为离线（容忍丢一拍）。
    · 客户端断线（ws.onclose）＝立即退出登录。

B2. 客户端自我状态自检（手机版 v1.32）
    · 页面**不在前台**（切走 App / 切标签，document.hidden）→ 发
      {'t':'logout'}，停止心跳（＝自动退出登录）。
    · **超过 5 分钟无任何操作**（无触摸/点击/按键/滚动）→ 同样自动退出。
    · 重新回到前台、或再次操作 → 自动重新 login。
    · 附带：操控「续占心跳」(ctl_hb) 也改为仅登录态才发——后台不再
      占着操控锁。

B3. ★ 广播闸门：无人在线 → 一律不广播
    · 服务端 forward_event 增加判据：**当前没有任何客户端登录在线时，
      直接丢弃所有远程事件**，不发送到中继。
    · 影响最大的是 msgs（AI 聊天记录，含全部历史）——这是最耗流量的
      一块，现在在无人观看时**彻底停发**。
    · 顺带停发的还有 models/积分/账号/附件列表等所有远程事件。
    · 本地服务端面板不受影响（走本地队列，与远程链路分离）。

B4. 登录即整包重放（_push_full）
    · 客户端 login / 回到前台时，服务端立刻整包重放（含 msgs），
      并记录指纹，避免下一拍重复发送。
    · 效果：不出现「回来了但界面是空的」——只在真正需要时传一次全量。

B5. 在线客户端数显示对齐
    · 「在线客户端数」统计窗口由 60 秒放宽到 150 秒，与登录超时一致，
      心跳往返期间不会在 0/1 之间闪跳。


────────────────────────────────────────────────────────────────────────────
四、协议与参数一览
────────────────────────────────────────────────────────────────────────────
客户端 → 服务端：
    {'t':'login', 'fg':true/false}   登录/回到前台（服务端随即整包重放）
    {'t':'hb',    'fg':true/false}   心跳（每 60 秒）
    {'t':'logout','r':'切后台'/'闲置5分钟'/'离开页面'/'断线'}   退出登录
    {'t':'hello'}                    请求当前状态（旧协议，保留兼容）
服务端 → 客户端：
    {'t':'ev','k':'snap'|..., 'v':...}   事件（仅在有客户端登录时发送）
    {'t':'hello', ...}                   状态 + 重放最新快照/模型

参数（服务端常量）：
    HB_SEC     = 60    客户端心跳间隔（秒）
    LOGIN_TMO  = 150   无心跳判下线（秒）＝ 2.5 × 心跳
    PEER_TMO   = 150   在线客户端数统计窗口（秒）
    KA_SEC     = 25    WS 链路保活心跳（秒）
    poll_sec   = 0.8   快照轮询间隔（秒）
参数（手机版常量）：
    HB_SEC   = 60        心跳间隔（秒）
    IDLE_MS  = 300000    5 分钟无操作判闲置（毫秒）


────────────────────────────────────────────────────────────────────────────
五、预期效果
────────────────────────────────────────────────────────────────────────────
· 手机放兜里 / 切后台 / 5 分钟没动：服务端**发 0 条**（此前仍在每 0.8 秒
  整包重发，尤其 AI 打字时几乎不停）。
· 只有真正盯着屏幕看时才传数据——「有人看才传」。
· 一台手机一天中真正前台查看的时间通常只有一两小时，其余时间由原来的
  「持续整包重发」变为「零发送」，这是本轮最大的一块节省。
· 注意：**前台查看看的时候流量不变**（仍是 0.8 秒一拍的全量快照）。
  若还要继续降，需要走「按消息 ID 增量同步」方向（见第七节）。


────────────────────────────────────────────────────────────────────────────
六、验收方法
────────────────────────────────────────────────────────────────────────────
1. 服务端界面「网络」页有收/发条数统计（_stats_add）。
   ① 手机上把页面切到后台，等 3 分钟；② 观察服务端「发送」条数应停止
   增长（AI 正在打字时也一样）；③ 手机切回前台，条数恢复增长。
2. 客户端登录状态可用浏览器控制台看：登录后每 60 秒发一次 hb；
   切后台立刻发 logout 并停发。
3. 隔离测试脚本：见工具目录 _测试脚本/（服务端登录态与闸门、手机端
   登录/心跳/退出逻辑）。


────────────────────────────────────────────────────────────────────────────
七、还能再降吗（后续可选方向）
────────────────────────────────────────────────────────────────────────────
本轮解决的是「没人在看也照发」。下一步若要降「有人在看时的量」，需要把
「全量快照整包重发」改为「按消息 ID 增量同步」：
    · TRAE 每条消息有稳定的 data-message-id（24 位十六进制）；
    · 死消息（无 streaming 标记）按 ID 收录一次，两端「我有这个 ID 就跳过」；
    · 活消息（唯一 streaming 那条）才实时推送；
    · 会话本身无 ID，需用「消息 ID 集合」或本地自增号对位。
详见《WS流量整改交接文档_给AI看.txt》第四~八节（含已实测验证的 DOM 事实
与「活→死不得有空白期」的过渡要求）。
